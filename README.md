# mihomo（Clash Meta）内核说明

mihomo是什么，适合先从内核与图形界面的关系理解；clashmeta、clash meta 是阅读旧资料时会遇到的写法，不能据名称把所有客户端当成同一项目。本文说明 mihomo 对应的项目入口、客户端自述和文档栏目，不提供配置模板或版本高低比较。

## 旧名称的重定向是一条入口关系

对 MetaCubeX 的 Clash.Meta 旧仓库名请求，已有接口记录返回 mihomo 的仓库全名。这能说明旧入口指向哪里，但不等于已经取得一份开发者改名公告。入口跳转与公告文字是两类资料，本文没有让前者替后者补齐历史叙述。

Clash Meta for Android 的 README 仍以 Clash.Meta 介绍所用内核，并链接旧入口。FlClash 则在自述中同时出现 mihomo 和 Clash.Meta。这些项目各自的名称用法可以并列，不需要替它们把所有旧写法统一改掉。

关于 mihomo 仓库首页，已有读取结果出现过与代理项目无关的内容，不能用于写内核特性或许可结论。本文采用的关系依据来自重定向、客户端 README 与明确的文档入口，不将异常文本解释成项目功能变化。

版本发布用 [mihomo 官方发布页](https://github.com/MetaCubeX/mihomo/releases) 表示，配置资料入口用 [mihomo 官方文档站](https://wiki.metacubex.one/) 表示。两个入口的用途不同，看到发布资产并不代表已经读到客户端界面说明。本文也没有将仓库名字本身当作许可资料。

## 图形界面与内核分别承担自己的角色

Verge Rev 的 README 将自身描述为基于 Tauri 的 Clash Meta 图形客户端，并说内置 Clash.Meta 内核，可切换 Alpha 内核。这里确认的是该客户端自己的组合，不把图形界面名字写成内核名字。打开一个客户端，不能仅凭标题识别它当前实际运行的内核版本。

FlClash 则自述为基于 mihomo、Clash.Meta 的多平台代理客户端。它列有配置输入、规则、代理组、连接及日志查看，属于应用层功能介绍。不能因为这些功能涉及代理，就把全部项目自述改成内核统一特性。

Clash Party 的介绍把自己定位为另一款 Mihomo 图形界面。它的功能、平台和发布资料有自己的来源，名字与另一个客户端相近并不构成界面互换的证明。项目中出现内核名，只确认该条已写明的联系。

图形应用、内核和配置之间可以按“谁显示界面、谁被调用、输入由谁读取”分别记录。这里是整理项目已说明的职责，不是在承诺存在统一插件接口。没有公开说明的数据互通和设置迁移，本文不填入关系中。

## 每个客户端只保留它自己的内核表述

Clash Meta for Android 的 README 明确将其写为 Android 上的 Clash.Meta 图形界面。该项目可以与 Verge、FlClash 的自述放在一起阅读，但不能把桌面项目的托盘功能补到 Android 项目。平台名与界面职责同样需要保持原主语。

ClashX.Meta 的资料有不同边界：所读 README 呈现原 ClashX 的说明，未直接写 Meta、mihomo。因此本文不只靠 Meta 后缀给它补一条已确认的内核绑定。其发布记录存在与内核说明缺少，可以同时成立。

旧 CFW 的快照描述基于 Clash 和 Electron，当前入口的读取结果则为 404。历史上存在某个图形应用，不是它今天已经采用 mihomo 的证明；上游引用和项目致谢也没有替它给出现行内核说明。旧客户端记录与当前项目关系不互相覆盖。

这些资料由 [Clash Verge Rev 官方发布页](https://github.com/clash-verge-rev/clash-verge-rev/releases)、[FlClash 官方发布页](https://github.com/chen08209/FlClash/releases)、[Clash Party 官方发布页](https://github.com/mihomo-party-org/clash-party/releases)、[Clash Meta for Android 官方发布页](https://github.com/MetaCubeX/ClashMetaForAndroid/releases) 分别指代。入口分开后，同一内核名出现在几个项目里，并不让各个项目的全部说明自动合并。

## 文档中的安装导航用于区分资料入口

mihomo 官方文档首页的导航含简介、安装、手册、配置与 APIs。安装部分又列安装、常见问题、客户端、web 面板、创建运行服务、三方工具或客户端等标题。这里能确认栏目存在，不据目录标题补出未读取的正文。

“客户端”和“web 面板”是不同导航项目。两者都能在文档入口看到，不代表其中任何一个就是内核本身；栏目名称也没有给某个具体客户端作推荐。本文保留目录用途，不把导航变成产品选择顺序。

手册下有语法与快捷配置。它们为读者提供不同主题的索引，但不能仅凭标题宣称配置内容已经覆盖某个特定场景。本文没有复制配置，也没有将目录页作为执行某条设置的证据。

通过这些导航可以建立阅读位置：项目入口看身份，客户端说明看应用功能，文档栏目看配置主题。位置之间存在联系，却不能让一个标题回答另一份正文尚未回答的问题。尤其是软件的系统要求，仍应回到对应客户端资料。

## 入站、出站与代理集合是不同配置主题

配置导航把入站与出站分列。入站栏目列有代理端口、TUN、listeners 及 HTTP、SOCKS、Mixed 等主题，出站目录则按各类协议与内置策略组织。目录是主题清单，不代表同一行列出的对象在配置里具有相同作用。

出站目录既有 Shadowsocks、Trojan、AnyTLS 等协议页，也有 DIRECT、DNS 等条目。不能将目录页数直接说成同样数量的外部代理协议，更不能从导航数量推出所有图形客户端都暴露了这些类型。本文只使用标题，不扩写协议能力清单。

订阅相关资料采用“代理集合”“代理集合内容”两个官方标题。它们与应用界面的订阅导入相关，但在文档中是内核配置主题，不是界面操作原文。某个客户端能用地址导入配置，并不说明它的按钮与内核字段逐字一致。

规则相关还有“路由规则”与“子规则”，另有“规则集合”及“规则集合内容”。本文不由这些标题补匹配语法、默认规则或完整范例；读者遇到哪个主题，只能确认这里有相应资料栏目。关系说明到主题位置为止，不替正文写实现细节。

## DNS、隧道与服务资料不能混作客户端承诺

DNS 导航下有类型、hosts 与解析流程，配置中另列域名嗅探、流量隧道、NTP、实验性配置。这些是内核文档的内容范围，不是某个应用在所有平台上的完整功能表。标题出现的位置要随名称一起保留。

客户端可能有自己的服务模式。Verge 文档说服务进程可以启动内核，并解释独立后台进程与界面退出的关系；这属于该应用的实现说明，不能套到每款基于同一内核的软件。共同内核不意味着相同服务安装方式。

FlClash 的桌面介绍列托盘、快捷键，Android 介绍则列分应用代理和快捷设置磁贴。这是客户端按平台组织功能的例子，不能删去平台后称为内核统一界面。文档的 TUN 标题同样不会直接给某个手机应用补菜单。

阅读关系时，内核文档和应用功能两边都需要自己的主语。某个功能名重复出现，只说明两份资料谈到相关主题；有没有同样默认值、同样开关或相同运行范围，必须另有明确说明。本文不从名称相同继续推断。

FlClash 在另一份 2026-10-23 发布源记录中出现预发布标签 v0.9.2-pre.2。它不能被省去标签后替代前一天稳定页的 v0.9.1，也不能用来给内核设置一个同名版本。客户端与内核的各自版本没有被合成统一编号。

对 mihomo 许可证，现有材料的读取结果存在差异，本文不写具体许可。对首页无法采用的特性文本，也不据记忆恢复一份完整列表。保留这些边界，避免让项目关系说明附带没有依据的法律或功能结论。

本文能交代的是旧入口去向、若干客户端已明示的内核联系，以及官方文档怎样组织主题。尚未明示的项目关系、跨项目兼容和默认值保持空缺，没有因为列表中并列项目就变成已经确认。关系清楚之后，具体配置仍由它自己的正文解释。

官方文档对下游项目名称另有约束：与 MetaCubeX 无关的下游名称不应包含 mihomo。本文只转述命名要求，不据某个第三方名字是否出现该词来判断授权或关系。实际项目归属仍需自己的声明，名称不能替代组织身份资料。

文档还有规则集合内容与代理集合内容，两者文字相近，却处在各自资料主题。本文只确认目录位置，不把它们都叫订阅文件，也不从“集合”两个字补输入格式或更新方式。涉及具体参数时，仍需要对应正文而非栏目标题。

客户端自述中的框架同样不代替内核说明。Verge 写 Rust、Tauri 2，FlClash 的构建资料列 Flutter、Go、Rust；这些是项目自己的开发资料，不会让本文得到一份统一图形层规范。关系说明因此始终保留项目主语。

## FAQ

### Clash.Meta 旧入口现在指向哪里？

接口记录返回 mihomo 仓库全名。这个入口关系不等于已经取得完整改名公告。

### Verge 的版本号就是内核号吗？

两者对应不同项目。客户端发布号不能自动证明当前运行内核的具体版本。

### 多个应用用同一内核，设置就能互换吗？

现有自述没有给出这种共同承诺。应用的输入、备份与服务方式仍需各自说明。

### ClashX.Meta 的名称能确认其内核吗？

所读 README 没写明确的对应关系。不能由名字把缺少的声明补齐。

### 文档目录就是全部客户端功能表吗？

目录按内核配置主题组织。客户端是否提供某种入口，不能由目录页数或标题代答。

### 这里为什么没有许可证和完整配置？

许可资料存在冲突，本文不采用具体结论。本文只解释项目关系与文档位置，不提供配置示例。

### 代理组标题能说明具体算法吗？

本文只取得部分栏目名称，没有相应正文。自动选择、回退或负载均衡这些标题不提供本文可用的算法参数，也不能推成所有客户端界面完全一致。

### 命名要求能证明某个下游获得授权吗？

文档给出命名约束，不提供本文某个实际项目的授权材料。本文没有由第三方名字判断组织关系，也不会把名称符合与否写成主体身份核验结果。
